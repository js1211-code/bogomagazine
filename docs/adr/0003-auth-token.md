# ADR-0003: 인증 토큰 방식 (짧은 JWT + 리프레시 토큰 교체)

- 상태: 제안 (팀 확정 전)
- 작성: 2026-10-04 11:36 KST
- 관련: [api-spec.md](../api-spec.md) 1-1, [api-spec-review.md](../api-spec-review.md)

## 배경

앱은 모바일(iOS 먼저, Android 나중)이 주 클라이언트이고 Admin은 웹이다. 로그인은 카카오·애플만 쓰고(ACC-01, ACC-02), 서버가 제공자 토큰을 검증한 뒤 **자체 세션 토큰**을 발급한다. 지금은 가족 10개, 구성원 50명 안팎의 테스트 규모이지만 확장을 고려한다.

검토한 질문과 결론은 다음과 같다.

- JWT는 토큰 **형식**이고 OAuth 2.0은 권한 위임 **프레임워크**다. 서로 대체 관계가 아니다.
- 카카오·애플 로그인은 이미 OAuth/OIDC이고 우리 서버는 그 결과를 받는 쪽이다.
- 직접 OAuth2 인증 서버를 두면 SSO·제3자 위임·scope를 얻지만, 자사 앱 하나와 Admin 하나인 현재 구조에서는 필요하지 않다.

## 선택지

| 방식 | 공수(추정) | 추가 비용 | 비고 |
| --- | --- | --- | --- |
| A. 짧은 JWT 액세스 + 불투명 리프레시(교체) | 2~4 인일 | 인프라 추가 없음 | 모바일에서 흔한 구성. 액세스 토큰은 만료 전까지 폐기할 수 없음 |
| B. 불투명 세션 토큰만 | 더 작음 | 인프라 추가 없음 | 즉시 폐기. 요청마다 조회 필요 |
| C. 관리형 인증 (Firebase Auth, Cognito, Auth0 등) | 3~7 인일 | 소규모는 무료 구간 (요금 확인 필요) | 카카오 사용자 지정 연동 필요, 사용자 정보가 외부에 저장됨 (보관 위치 확인 필요) |
| D. 자체 OAuth2 인증 서버 (Spring Authorization Server, Keycloak) | 2~4주 이상 + 운영 | 서버 1대 추가 | 인프라 한도(월 10만 원, NFR-19)에 부담 |

공수는 추정치이고 팀 숙련도에 따라 달라진다.

## 결정 (제안)

**A를 쓴다.** 나중에 C 또는 D로 옮길 수 있도록 아래 원칙을 지킨다.

1. **액세스 토큰**: JWT, 만료 10~15분. 클레임은 `sub`(내부 사용자 UUID), `exp`, `iss`, `aud`, `jti`만 둔다. 가족·역할은 넣지 않고 요청마다 DB(또는 짧은 TTL 캐시)로 확인한다.
2. **서명**: 비대칭(ES256 또는 EdDSA), `kid`로 키 교체, 공개키 목록(JWKS) 제공. `none` 알고리즘은 거부한다.
3. **리프레시 토큰**: JWT가 아닌 불투명 랜덤 값. 서버가 해시로 저장하고 기기별 1개, 사용할 때마다 교체한다. 이미 사용한 토큰이 다시 오면 해당 계정의 리프레시 토큰을 모두 폐기한다 (탈취 감지).
4. **폐기**: 로그아웃은 해당 기기의 리프레시 토큰, 탈퇴는 전체를 폐기한다. 즉시 차단이 필요해지면 `jti` 폐기 목록을 캐시에 둔다.
5. **발급은 `/auth/*` 한 곳**에 모으고 검증은 Spring Security의 표준 JWT 검증을 쓴다. 외부 인증 서비스로 옮길 때 발급부만 교체한다.
6. **Admin**: 별도 `aud`와 별도 토큰, 만료를 더 짧게 둔다. 웹이므로 HttpOnly 쿠키 세션도 선택지다.
7. **앱 저장**: Keychain(iOS)/Keystore(Android). 일반 저장소는 쓰지 않는다.
8. **남용 방어**: 로그인·갱신 요청에 횟수 제한을 둔다.
9. **버전**: `/api/v1`, 최소 지원 앱 버전 확인(`X-App-Version`).

## 정해야 할 값

| 항목 | 후보 |
| --- | --- |
| 액세스 토큰 만료 | 10분 / 15분 |
| 리프레시 토큰 만료 | 30일 / 60일 / 90일 |
| 기기당 리프레시 토큰 | 1개 (재로그인 시 교체) |
| JWT 대신 불투명 토큰만 쓸지 | B 선택 시 JWT 서명·키 관리가 필요 없어짐 |
| 로그인 엔드포인트 | `/auth/kakao` + `/auth/apple` 분리 / `/auth/login` + `provider` |

## 결과

- 장점: 별도 인증 서버 없이 시작할 수 있고, 액세스 토큰 검증은 서버를 늘리면 선형으로 확장된다. 이후 외부 인증 서비스로 이전할 때 API 변경이 작다.
- 단점: 액세스 토큰 만료 전까지는 폐기가 즉시 반영되지 않는다. 리프레시 교체·재사용 감지를 직접 구현해야 한다.
- 재검토 시점: 웹 클라이언트나 파트너 앱이 생겨 로그인을 공유해야 할 때, 서비스를 분리할 때, Admin 계정·다단계 인증·감사 로그 요구가 늘 때, 보안 인증이나 외부 점검 요구가 생길 때.

## DB 변경

현재 `auth_identity.refresh_token_ref`는 애플 해지용(제공자 토큰)이다. 우리 리프레시 토큰을 저장하는 곳이 아니므로 테이블이 새로 필요하다.

```
refresh_token
  id           uuid PK
  user_id      uuid NOT NULL → app_user
  device_id    uuid → device
  token_hash   text NOT NULL UNIQUE
  expires_at   timestamptz NOT NULL
  rotated_at   timestamptz
  revoked_at   timestamptz
  created_at   timestamptz NOT NULL DEFAULT now()
```

- 만료·폐기된 행은 정기 작업으로 삭제한다.
- 운영자 인증은 `operator`에 `password_hash`(Argon2/bcrypt) 또는 SSO 식별자를 추가해야 한다 (현재 인증 컬럼 없음).

## API 영향

- `POST /auth/refresh`: 리프레시 토큰을 받아 새 액세스·리프레시 토큰을 발급한다. 이미 사용된 토큰이면 `401` 후 해당 계정의 토큰을 폐기한다.
- `POST /auth/logout`: 해당 기기의 리프레시 토큰을 폐기한다.
- `DELETE /me`: 해당 계정의 모든 리프레시 토큰을 폐기한다.
- 앱: `401` 수신 시 갱신을 한 번만 시도(동시 요청은 합침)하고 실패하면 로그인 화면으로 이동한다.
