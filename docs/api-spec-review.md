### 1-4. 호 주기

기능명세서: 2주 × 1호, 호 시작 월 07:00, 마감 2주차 일 23:59, 모든 가족이 같은 일정, 테스트는 1호뿐이라 다음 호를 배정하지 않는다 (D-04, POST-07, 운영 흐름표).

현재 DB: 가족방별 `close_day`(다음 달 N일)와 `timezone`, 매월 호를 자동 생성하는 배치(`open_monthly_issues`, `run_monthly_batch`). `V001` 머리말에는 "필드 테스트는 2주"라고 적혀 있으나 구현된 로직은 월 단위다.

차이: 필드 테스트 일정(2주, 전 가족 동일)을 현재 배치로 구성할 수 없다. 호 시작·마감을 운영자가 지정하는 방식(`POST /admin/issues/open`)이면 `close_day`, `timezone`, 월 배치가 필요하지 않다. 정식 출시 주기는 정해지지 않았다 (D-04).

참고: 와이어프레임에는 제1·2·3호, 11/03·11/17 발행이 보인다. 이는 화면 예시이고 기능명세서의 테스트 기준(1호)과 다르다.

## 2. 구조상 검토가 필요한 부분

### 2-1. 초대 링크 저장 방식 (DB 반영 필요)

`family_invite.token_hash`는 토큰 원문을 저장하지 않는다. 기능명세서는 구성원 누구나 언제든 같은 링크를 공유하고 재발급이 없다고 정한다 (FAM-05). 1004 명세는 링크 원칙을 "가족마다 고정 초대 코드 1개(추측하기 어려운 문자열), 형태 `https://{도메인}/i/{코드}`"로 구체화했다. 원문이 저장되어 있지 않으면 첫 생성자 이외의 구성원은 링크를 다시 얻을 수 없다.

선택지

| 방식 | 내용 |
| --- | --- |
| A | 토큰을 저장하지 않고 `HMAC(서버 비밀키, group_id)`로 계산한다. 가족당 링크가 하나로 정해지고 `family_invite` 테이블이 필요하지 않다. 비밀키가 노출되면 모든 링크가 영향을 받는다 |
| B | `family_group.invite_token`에 원문을 저장한다 (유니크 인덱스). DB가 노출되면 링크도 노출된다 |

유저 플로우는 링크가 유효하지 않은 경우(만료·잘못된 링크)를 별도 오류 화면으로 정의한다. 링크를 무효화하는 조건이 생기면 방식 A는 별도 상태 저장이 필요하다 ([4-2](#4-2-1004-명세와-유저-플로우와이어프레임이-같은-방향이지만-확정이-필요한-항목) 참조).

### 2-2. 탈퇴·가족 삭제를 막는 구조

기능명세서는 탈퇴 시 개인정보를 지체 없이 파기하고(NFR-09), 마지막 구성원이 탈퇴하면 가족방과 모든 기록을 삭제한다고 정한다 (ACC-05). 현재 스키마는 삭제를 막는 제약을 두고 있다.

| 제약 | 위치 | 영향 |
| --- | --- | --- |
| 호가 있으면 가족방 삭제 불가 | `issue.group_id → family_group` (CASCADE 없음) | 마지막 구성원 탈퇴 시 가족 삭제 불가 |
| 인쇄 작업이 있으면 호 삭제 불가 | `print_job.issue_id → issue` | 동일 |
| 조판에 배치된 사진의 글은 삭제 불가 | `placement.media_id → media`, 트리거(T115) | "마감 후 탈퇴 시 앱 데이터 삭제" 구현 불가 |
| 데이터가 있는 사용자는 삭제 불가 | 여러 FK | 탈퇴는 익명화(`anonymize_user`)만 가능하고 글·사진은 남음 |

`TODO.md`의 "삭제 정책"(결정 대기)이 기능명세서에서 결정된 상태다. 구현에 필요한 항목은 다음과 같다.

1. 탈퇴 시 앱 노출 데이터를 즉시 삭제 처리(소프트 삭제)하고, 마감된 호의 인쇄용 원본은 발송 완료(`SENT`)까지 보관한 뒤 파기하는 규칙.
2. 가족 삭제 경로: 자식 테이블 CASCADE 또는 삭제 전용 함수(스토리지 객체 삭제는 DB 트랜잭션 밖이라 실패 처리가 별도로 필요).
3. 마지막 구성원 탈퇴 시 진행 중인 호를 발송 대상에서 제외하는 처리.

### 2-3. 호 상태 수

기능명세서의 상태는 4단계이고 사용자와 운영자가 같은 이름을 쓴다 (PUB-01). DB는 `collecting`, `closing`, `review`, `printing`, `printed`, `skipped`, `archived` 7개와 전이 12개, 사전조건 함수, 전이표 테이블(`issue_status_transition`)을 갖는다.

- `skipped`(수량 미달 미발행): 명세에 없다. `family_group.auto_skip_below_min`, `issue.min_photos`·`min_pages`가 이 상태와 관련된다.
- `review → printing` 수동 전환: 명세의 수동 전환은 '발송 완료' 하나다.
- `archived`: 가족 화면에서 쓰이지 않는다.

API 명세서는 4단계로 접어서 노출한다 (부록 B). DB를 4단계로 줄이면 변환이 필요 없어지고, 줄이지 않으면 두 어휘를 계속 대응시켜야 한다.

### 2-4. 지표 산출

ADM-06(M-01~M-13)의 재료는 대부분 DB에 있다. 확인할 점은 다음과 같다.

- M-01(마감 시점 구성원 수): 재합류하면 `family_member`의 같은 행을 되살리며 `joined_at`을 덮어쓴다(`accept_family_invite`). 한 번 나갔다가 돌아온 사람의 이전 합류 기록은 남지 않는다. 마감 시점 값을 스냅샷으로 저장하면 이 영향이 없다.
- M-02·M-03·M-06(마감 전 삭제분 제외): 삭제를 `deleted_at`으로 처리하면 구현할 수 있다. 탈퇴 시 모집 중 게시물을 물리 삭제하면 M-04(참여 구성원 수)에서 탈퇴자의 참여가 빠진다. 탈퇴자의 참여를 지표에 포함할지는 정해지지 않았다.
- M-10(리마인더 후 참여): `notification_log`의 `kind = 'deadline_reminder'`, `sent_at`을 사용한다.
- M-12(신문 열람): `newsletter_view_log`가 있다. `print_job`에 연결되어 있어서 같은 호에 재인쇄가 있으면 호 단위 집계에 조인이 필요하다.
- M-13(대기 신청): `waitlist_signup`.

### 2-5. 부부 수신 질문의 대상 (DB 반영 필요, 미결 O-09)

QST-07: 부부 수신이면 이번 주는 할머니, 다음 주는 할아버지처럼 번갈아 출제한다. `issue_question`에는 질문이 어느 분을 향한 것인지 저장하는 컬럼이 없다. 호칭을 질문마다 계산하려면 대상(여성/남성)을 저장할 컬럼이 필요하다. 출제 순서가 미결이다 (O-09).

### 2-6. 호 번호(`issueNo`)

와이어프레임은 "제 3호", "제 2호"처럼 가족별 호 번호를 표시한다. DB `issue`에는 번호 컬럼이 없고 `title`만 있다. API 명세서는 `issueNo`를 가족 안에서 `period_start` 순으로 센 값(파생값)으로 정의했다. 번호를 저장해야 하는지는 호 제목 규칙에 따라 달라진다. 테스트가 1호이므로 현재 범위에서는 파생값으로 충분하다.

### 2-7. 템플릿 테이블

`template`, `page_master`, `style`, `font` 4개 테이블은 불변 버전 구조를 갖춘다. 기능명세서는 "규칙 기반 템플릿 선택"(NEWS-01)과 "템플릿은 코드와 분리"(NFR-17)를 정하고 판형은 보류 상태다 (D-26, O-06). 설정 파일 형태도 NFR-17을 만족한다. `issue.template_id`, `layout_run.template_id`가 이 테이블을 참조하므로 판형이 정해진 뒤에 구조를 다시 검토하는 편이 변경 범위가 작다.

### 2-8. 행위자 검증

DB 함수는 `p_actor`를 앱이 넘긴 값으로 신뢰하고, 방장·본인 검사는 앱 코드에 의존한다 (`architecture.md`의 "한계", TODO "DB 권한 분리"). 초대·배송지 권한 규칙이 바뀌면 DB 가드와 API 가드를 함께 수정해야 두 곳이 어긋나지 않는다.

### 2-9. API 설계 변경 내역

| 이전 초안 | 문제 | API 명세서 |
| --- | --- | --- |
| 피드 `page/size` | 새 글이 올라오면 다음 페이지에서 중복·누락 | 커서 페이지네이션 (피드, 댓글, 알림) |

## 4. 유저 플로우·와이어프레임과 1004 명세의 차이

유저 플로우(2페이지)와 와이어프레임(화면 24개)은 1002 명세 시점에 그려졌을 가능성이 있고, 1004 명세와 다른 곳이 있다. 항목별 비교표는 [api-spec.md 부록 F](api-spec.md#부록-f-확인이-필요한-항목)가 기준이다. 여기에는 요약과 DB 영향만 적는다.

### 4-1. 1004 명세 기준으로 API를 정리한 항목

- 하단 탭: 소식·질문·가족 + 우상단 설정 (와이어프레임은 홈·질문·마이)
- 알림 목록: 소식·질문 헤더의 종 아이콘, 가족 탭에는 없음
- 호 선택: 공유 헤더에서 호를 고르면 소식·질문카드 탭이 함께 바뀜. 호가 1개면 호 목록을 열 수 없음
- 상태 줄: 시작 전 / 모집 중(D-day) / 신문 만드는 중 / 발송 완료. D-day는 날짜 기준(KST)이고 마감 당일이 "D-day"
- 가입 중 프로필 사진 없음, 받는 분 사진은 가족 생성 후 업로드
- 대기 신청: 버튼 하나, 진입 경로 3가지 (와이어프레임의 3지선다 "시범 종료 선택"은 1004 명세에 없음)
- 마감 경계: 마감 전에 시작한 사진 업로드는 마감 후 14분까지 등록, 자동 조판은 00:15 이후
- 신문 열람: 서버가 만든 열람용 페이지 이미지를 가로로 넘겨 봄, 마지막 면 다음 장에 대기 신청 카드
- 내보낸 구성원 목록과 "재합류 허용" (1002 명세의 "차단 해제")

### 4-2. 1004 명세와 유저 플로우·와이어프레임이 같은 방향이지만 확정이 필요한 항목

로그인 수단(애플 버튼), 가입 동의 항목, 생일 형식(월·일 / `YYYY-MM-DD`), 받는 분 생일·성별 입력란, 관계 선택지, 가제트 이름과 신문 제호, 홈의 "모인 수", 초대 링크 "만료" 오류 화면, 관계 입력 시점, 선택형 답변 화면.

### 4-3. 1004 명세에서 정해지지 않은 항목

앱을 나갔을 때 업로드·작성 중인 글의 처리, 지난 주차 질문의 답변 열람 제한, 마지막에 본 가족의 저장 위치, 글자 수·사진 수 상한(O-05), 저해상도 기준(O-08), 제호 변경 권한(O-14), 내보낸 사람의 게시물(O-17), 신고 사유(O-24) 등. 목록은 [api-spec.md 부록 F-3](api-spec.md#부록-f-확인이-필요한-항목)에 있다.

### 4-4. 1004 명세로 인한 DB 영향

| 항목 | 내용 |
| --- | --- |
| 알림 | `notification_log`에 열람·읽음 상태, 방장 변경 `kind`, 60일 삭제 규칙이 필요하다 (NOTI-06, FAM-11) |
| 업로드 시작 시각 | 마감 경계 14분 규칙(POST-07)에 필요하다 |

### 6-2. 1005 명세로 인한 DB 영향

| 항목 | 내용 |
| --- | --- |
| 캐릭터 | 구성원·받는 분마다 캐릭터를 저장할 곳이 없다. 가족방 안에서 색 + 머리·소품이 겹치지 않게 배정하는 규칙이 필요하다 (PRF-05). `app_user.photo_key`, `delivery_address.recipient_photo_key`는 쓰지 않게 된다 |
| 신문 제호 | `family_group.newsletter_title`을 그대로 쓴다 (삭제 후보에서 제외) |
| 생일 안내 | `app_user.birth_month/day`로 마감일 기준 30일 안 생일을 계산한다 |
| 중복 생성 방지 | 가족 만들기의 멱등 키 저장 (`idempotency_key`) |
| 답변 현황 | 답변 여부 조회 쿼리. 새 컬럼은 필요 없다 |
| 대기 신청 노출 | "다음 회차 구독이 없는 가족방" 판단 값이 없다. 구독·회차 개념이 아직 DB에 없어 판단 방식(예: 다음 호 존재 여부)을 정해야 한다 |

### 6-3. 사용자 시나리오로 확인할 점

- 가입 → 이름 확인 → 초대가 있으면 합류 분기, 없으면 가족방 없음 화면 (ACC-01).
- 초대받은 사람과 이미 가입한 사람의 관계 선택 화면이 같고 안내 문구만 다르다 (FAM-04).
- 내보낸 구성원이 링크를 누르면 "이 가족에는 참여할 수 없어요"이고, 다른 가족방이 있으면 [내 가족방으로 가기], 없으면 가족방 없음 화면이다 (FAM-07, O-31).
- 이미 구성원인 링크는 소식 탭으로 이동하고 토스트("이미 함께하고 있는 가족방이에요")를 보인다 (FAM-07).
